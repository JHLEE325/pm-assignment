# 산출물 A — 데이터 진단과 기준 정하기

## A-1. 데이터를 그냥 더하면 틀리는 지점

### 1. Worklog 시간 단위가 혼재되어 있음

#### 1) 무엇을 발견했는가

`jira_worklog.csv`의 `time_spent`는 숫자이지만 `unit` 컬럼에는 `h`와 `d`가 함께 존재한다.

예를 들어 `HRG-1013`의 worklog에는 다음 기록이 있다.

- 8h
- 8h
- 1d
- 6h

따라서 `time_spent` 값만 단순 합산하면 `8 + 8 + 1 + 6 = 23`이 되어 실제 작업량을 올바르게 나타내지 못한다.

#### 2) 왜 문제인가

버전별 실제 MD를 계산할 때 단위 변환 없이 `time_spent`를 합산하면 `d` 단위가 기록된 이슈의 `time_spent`가 과소 계산된다.

이 오류는 이후 MD 기준표 갱신에도 그대로 반영되어 다음 버전의 일정 역산 결과까지 왜곡할 수 있다.

#### 3) 어떻게 처리할 것인가

모든 worklog를 공통 시간 단위로 변환한 후 계산한다.

1 MD의 구체적인 정의는 A-2에서 정하되, 변환 후에는 모든 값을 `hours` 또는 `days` 단위로 통일하여 저장한다.

#### 4) 이 처리의 부작용은 무엇인가

`1d`가 정확히 몇 시간인지는 조직의 시간 설정에 따라 달라질 수 있다.

따라서 임의로 시간을 고정하기보다는 조직의 설정에 따라 유동적으로 계산할 수 있게 변수처리 하여야 한다.

---

### 2. 하나의 이슈에 여러 Fix Version이 존재함

#### 1) 무엇을 발견했는가

`jira_issues.csv`의 `fix_version`은 대부분 하나의 버전이지만 일부 이슈에는 여러 버전이 함께 기록되어 있다.

예:

- `HRG-1031`
- `fix_version = v1.8,v1.9`

#### 2) 왜 문제인가

버전별 MD를 계산하면서 `v1.8`과 `v1.9` 양쪽에 같은 이슈의 worklog를 모두 포함하면 동일한 작업량이 두 번 집계된다.

반대로 임의로 한 버전에만 포함하면 이전 버전에서 실제 사용한 `time_spent`를 잃을 가능성이 있다.

#### 3) 어떻게 처리할 것인가

현재 `fix_version` 값만으로 바로 집계하지 않는다.

Jira의 Fix Version 변경 이력을 확인하여 실제 작업 시점에 어느 버전에 속해 있었는지 판단할 수 있도록 한다.

CSV만으로 분석해야 하는 단계에서는 복수 버전 이슈를 별도 예외 목록으로 분리하고 자동 집계 대상에서 바로 확정하지 않는다.

#### 4) 이 처리의 부작용은 무엇인가

변경 이력을 기준으로 버전을 나누려면 현재 제공된 정리 CSV만으로는 충분하지 않을 수 있으며 Jira changelog 정보가 추가로 필요하다.

또한 하나의 이슈가 실제로 두 버전에 걸쳐 작업된 경우 `time_spent`를 어느 기준으로 분할할지 추가 정의가 필요하다.

### 3. Worklog가 없는 이슈가 존재함

#### 1) 무엇을 발견했는가

`jira_issues.csv`에는 이슈가 존재하지만 `jira_worklog.csv`에는 해당 이슈의 작업 기록이 없는 경우가 있다.

따라서 현재 존재하는 worklog만 단순 합산하면, 실제로 작업이 있었지만 기록되지 않은 이슈의 `time_spent`가 전체 MD에서 빠질 수 있다.

#### 2) 왜 문제인가

버전별 총 MD를 계산할 때 worklog가 존재하는 이슈만 합산하면 결과는 실제 총 투입 MD가 아니라 **기록된 MD의 합계**가 된다.

즉 worklog 누락 비율이 높을수록 버전별 실제 투입량이 과소 계산될 가능성이 있다.

#### 3) 어떻게 처리할 것인가

A-1에서는 worklog 결측이 단순 합산 결과를 왜곡할 수 있는 위험으로 식별한다.

실제 결측 비율, 결측이 특정 버전·직군·이슈 유형에 편중되어 있는지 여부, 결측값을 어떻게 처리할지는 **A-3에서 별도로 계산하고 상세하게 정의한다.**

#### 4) 이 처리의 부작용은 무엇인가

결측 worklog를 임의로 추정하지 않으면 실제 총 MD를 완전히 복원할 수 없다는 한계가 남는다.

반대로 추정값을 실제값처럼 보정하면 잘못된 가정이 기준 MD와 이후 일정 계산에 반영될 수 있으므로, 관측값과 추정값을 구분해서 관리해야 한다.

### A-2. 정의가 없는 항목을 직접 정하기

#### 1. 1 MD의 정의

1 MD는 **사람 1명이 하루 동안 실제로 투입하는 작업량**으로 정의한다.

본 과제에서는 1일의 기준 근무시간을 8시간으로 보고,
8시간의 작업 기록을 1 MD로 환산한다.

여러 사람이 하나의 이슈를 동시에 작업한 경우에는 각 사람이 실제 투입한 시간을 각각 MD로 환산한 뒤 합산한다.

예를 들어 한 이슈에 두 사람이 각각 8시간과 4시간을 작업했다면,

- 작업자 A: 8시간 = 1 MD
- 작업자 B: 4시간 = 0.5 MD
- 해당 이슈의 총 투입량: 1.5 MD

로 계산한다.

#### 2. 이슈를 어느 공정에 귀속시킬 것인가

제공 데이터에는 이슈의 공정을 직접 나타내는 필드가 없다.

따라서 본 과제에서는 이슈의 `assignee`나 이슈 제목만으로 공정을 결정하지 않고,
**실제 worklog를 작성한 사람의 `role`을 기준으로 공수를 공정에 귀속한다.**

`people.csv`에 정의된 role을 다음과 같이 매핑한다.

| people.role | 공정 |
|---|---|
| planner | PLAN |
| server | DEV |
| client | DEV |
| art | ART |

`people.csv`에는 실제로 planner, server, client, art 역할이 구분되어 있으며,
내부 아트와 외주 아트 모두 role은 `art`로 등록되어 있다.

따라서 Jira worklog의 `author`를 `people.csv.person`과 연결한 뒤,
작성자의 role에 따라 해당 worklog의 MD를 공정별로 집계한다.

예를 들어 하나의 이슈에 다음과 같은 worklog가 존재한다면,

- planner 8시간
- server 16시간
- art 8시간

이 이슈 전체를 하나의 공정으로 귀속하지 않고,

PLAN = 1 MD  
DEV = 2 MD  
ART = 1 MD

로 각각 분리하여 기록한다.

이 방식을 사용하는 이유는 `assignee`가 현재 책임자를 나타낼 뿐,
실제 작업에 참여한 모든 직군을 나타내지는 않기 때문이다.
작업 도중 담당자가 변경될 수도 있고,
하나의 이슈에 여러 직군이 함께 작업할 수도 있다.

따라서 실제 MD 산정에서는 `assignee`보다 worklog의 `author`를 우선한다.

단, worklog의 author가 `people.csv`에 존재하지 않거나
role을 공정으로 매핑할 수 없는 경우에는 임의로 특정 공정에 포함하지 않고
`UNCLASSIFIED`로 별도 관리한다.

#### 3. QA MD는 측정할 수 있는가

현재 제공 데이터에는 QA 담당자나 QA role이 존재하지 않고,
QA 담당자의 worklog도 확인할 수 없으므로 실제 QA MD를 직접 측정할 수 없다.

따라서 본 과제에서는 QA와 직접 연결된 데이터 중
가장 가까운 대체값으로 **`QA 반려` Bug 이슈에 기록된 worklog 합계**를 사용한다.

예를 들어 `QA 반려 1차`, `QA 반려 2차`와 같은 Bug 이슈의
worklog를 1 MD = 8시간 기준으로 환산하여 QA 관련 공수의 대체값으로 사용한다.

다만 해당 worklog의 작성자는 개발자이므로,
이 값은 실제 QA 담당자가 테스트에 사용한 시간이 아니라
QA 반려 이후 발생한 수정 공수에 가깝다.

따라서 이 값을 실제 QA MD와 동일한 값이라고 보지는 않으며,
현재 제공 데이터에서 QA 단계의 공수를 추정하기 위한 임시 지표로만 사용한다.

향후 QA 담당자의 실제 worklog 또는 테스트 수행시간 데이터가 확보되면
이 대체값 대신 실제 QA MD를 사용한다.

#### 4. 리소스 MD는 어디까지 포함하는가

리소스 MD에는 **내부 아트 인력과 외주 아트 인력의 실제 worklog를 모두 포함한다.**

`people.csv`에는 내부 아트 인력과 함께 다음 두 개의 외주 계정이
각각 별도의 `person`으로 등록되어 있다.

- `art_outsource01`
- `art_outsource02`

본 과제에서는 별도의 추가 정보가 없으므로
**외주 계정 1개를 작업자 1명으로 간주한다.**

따라서 내부 인력과 동일하게
한 계정이 기록한 8시간을 1 MD로 환산한다.

예를 들어 `art_outsource01`이 특정 이슈에 총 40시간의 worklog를 남겼다면

40시간 / 8시간 = 5 MD

로 계산한다.

같은 이슈에 `art_outsource01`, `art_outsource02`가 모두 작업했다면
각 계정의 worklog를 각각 독립적인 작업자의 공수로 계산한 뒤 합산한다.

외주 계정의 worklog 역시 실제 프로젝트 산출물을 만들기 위해 투입된 공수이므로
버전별 ART MD 및 전체 실제 MD 계산에 포함한다.

#### 5. "버전이 종료됐다"는 시점은 언제인가

본 과제에서는 **Jira에서 해당 Version을 Close한 날을 버전 종료 시점으로 정의한다.**

계획 배포일은 실제 작업 종료 시점이 아니라 목표 일정이므로
실적 MD를 확정하는 기준으로 사용하기 어렵다.

실제 배포일 역시 서비스에 기능이 반영된 시점이라는 의미는 있지만,
그 시점에 Jira상의 작업 기록이 모두 정리되었다고 보기는 어렵다.

실제 배포 이후에도 다음과 같은 변경이 발생할 수 있다.

- 누락된 worklog 입력
- 잘못 입력된 worklog 수정
- 이슈 reopen
- 상태 변경
- Fix Version 수정

본 과제의 목적은 버전별 실제 MD를 계산하고
그 결과를 다음 baseline에 반영하는 것이므로,
**어느 시점의 데이터를 최종 실적으로 확정할 것인지 명확한 기준이 필요하다.**

따라서 Jira Version Close를
해당 버전의 데이터가 운영상 확정된 시점으로 간주한다.

제공된 일정에서도 실제 배포일과 Jira Close일은 서로 다른 경우가 있다.

예를 들어,

v1.8은
- 실제 배포일: 2025-09-15
- Jira Close일: 2025-10-10

이며,

v2.0은
- 실제 배포일: 2026-01-19
- Jira Close일: 2026-02-06

이다.

이처럼 실제 배포 후에도 일정 기간 Jira Version이 열린 상태로 유지되는 사례가 있으므로,
실제 배포일보다 Jira Close일이
실적 데이터를 최종 확정하는 시점으로 더 적합하다고 판단한다.

따라서 운영 규칙은 다음과 같이 정의한다.

실제 배포
→ Jira 이슈 및 worklog 정리
→ Jira Version Close
→ 해당 시점의 실제 MD 확정
→ baseline 갱신

단점은 실제 배포 후 Jira Close까지 시간이 길어질 경우
baseline 갱신 시점도 늦어진다는 점이다.

본 과제에서는 빠른 갱신보다
확정되지 않은 데이터를 baseline에 반영하는 위험을 더 크게 보고,
Jira Close일을 최종 종료 기준으로 사용한다.

#### 6. S / M / L의 객관적인 기준

Size 판단에는 작업 시작 전에 확인할 수 있는
`orig_estimate`(최초 추정 공수)를 사용한다.

기존 `size_label`은 기획자가 주관적으로 입력한 값이므로
새로운 S / M / L 경계를 결정하는 기준으로 사용하지 않는다.


##### 공정별 Size를 별도로 계산

같은 CONTENT 또는 SYSTEM에 속하더라도
기획, 개발, 아트의 작업량은 서로 다를 수 있다.

예를 들어 같은 CONTENT 작업이라도
기획은 L 규모이고 개발은 M 규모일 수 있다.

따라서 하나의 Size를 모든 공정에 공통으로 적용하지 않고,

- CONTENT / PLAN
- CONTENT / DEV
- CONTENT / ART
- SYSTEM / PLAN
- SYSTEM / DEV
- SYSTEM / ART

별로 Size 기준을 각각 계산한다.

Jira 이슈의 `assignee`를 `people.csv`와 연결하여 공정을 구분하고,
각 그룹의 과거 `orig_estimate` 분포를 분석하였다.


##### S / M / L 경계 설정

기존 S / M / L 값을 정답으로 사용하지 않고,
각 `category × process`의 `orig_estimate` 분포를 세 구간으로 나누었다.

분포의 1/3 지점을 S의 상한,
2/3 지점을 M의 상한으로 사용하고,
1 MD = 8시간 기준에 맞추어 8시간 단위로 정리하였다.

그 결과 PLAN과 DEV의 초기 기준은 다음과 같다.

| Category | 공정 | S | M | L |
|---|---|---|---|---|
| CONTENT | PLAN | 32h 이하 | 32h 초과 ~ 56h 이하 | 56h 초과 |
| CONTENT | DEV | 32h 이하 | 32h 초과 ~ 88h 이하 | 88h 초과 |
| SYSTEM | PLAN | 72h 이하 | 72h 초과 ~ 136h 이하 | 136h 초과 |
| SYSTEM | DEV | 72h 이하 | 72h 초과 ~ 192h 이하 | 192h 초과 |

예를 들어 CONTENT 기획 이슈의 `orig_estimate`가 48시간이라면
CONTENT / PLAN / M으로 분류한다.

반면 같은 CONTENT의 개발 이슈가 `orig_estimate` 24시간이라면
CONTENT / DEV / S로 분류한다.

따라서 동일한 콘텐츠에서도 공정마다 서로 다른 Size가 적용될 수 있다.


##### ART / QA Size의 초기 기준

ART와 QA는 현재 제공 데이터만으로 PLAN / DEV와 동일한 방식의
객관적인 Size 경계를 충분히 도출하기 어렵다.

따라서 초기 운영 단계에서는 기존 `md_baseline_v0.csv`에 정의된
S / M / L별 ART / QA MD를 참고값으로 사용한다.

기존 baseline 자체는 검증된 값이 아니므로 이를 정답으로 간주하지 않고,
각 Size 대표값 사이의 중간점을 초기 경계값으로 사용한다.

초기 기준은 다음과 같다.

| Category | Process | S | M | L |
|---|---|---:|---:|---:|
| SYSTEM | ART | 4MD 이하 | 4MD 초과 ~ 9MD 이하 | 9MD 초과 |
| CONTENT | ART | 7MD 이하 | 7MD 초과 ~ 18MD 이하 | 18MD 초과 |
| SYSTEM | QA | 2MD 이하 | 2MD 초과 ~ 5MD 이하 | 5MD 초과 |
| CONTENT | QA | 2MD 이하 | 2MD 초과 ~ 3MD 이하 | 3MD 초과 |

이 값은 실제 데이터로 검증된 기준이 아니라
초기 운영을 위한 임시 기준이다.

향후 ART 이슈의 `orig_estimate`와 QA 예상 공수를
작업 시작 전에 기록하도록 하고,
충분한 실적이 쌓이면 PLAN / DEV와 동일하게
과거 예상 공수 분포와 실제 공수를 이용해 경계값을 재산정한다.

#### 7. "안정적인 기획 일정"의 정의

기존 `md_baseline_v0.csv`의 `review_days`, `art_lead_days`는
초기에 수기로 작성된 뒤 실제 데이터로 검증된 적이 없으므로,
안정적인 기획 일정의 기준으로 그대로 사용하지 않는다.

대신 기준일 현재 Jira Version이 종료된 v1.3 ~ v1.9의
실제 Jira 일정 데이터를 이용해 새로운 기준을 정의한다.


##### 1) 기획은 개발 착수 며칠 전에 끝나야 하는가

제공 데이터에는 별도의 검수 시작일과 종료일이 존재하지 않는다.

따라서 동일 작업에서

`기획 이슈의 resolved → 개발 이슈의 최초 started`

사이의 영업일 차이를
기획 완료 후 검수 및 인계에 확보된 기간의 대체값으로 사용한다.

분석 결과는 다음과 같다.

| Size | 분석 건수 | 중앙값 | 75% 지점 |
|---|---:|---:|---:|
| S | 16 | 2일 | 2.25일 |
| M | 16 | 3일 | 4일 |
| L | 12 | 5일 | 6일 |

안정적인 일정은 일반적인 중앙값보다 조금 더 여유 있게 잡기 위해
75% 지점을 기준으로 한다.

영업일 단위로 적용할 수 있도록 올림하여 다음과 같이 정의한다.

| Size | 기획 완료 기준 |
|---|---:|
| S | 개발 착수 3영업일 전 |
| M | 개발 착수 4영업일 전 |
| L | 개발 착수 6영업일 전 |

즉 M 규모의 기획이라면
최소 개발 착수 4영업일 전까지 기획이 완료되어야
안정적인 일정으로 본다.

단, `resolved → started` 사이가 실제 검수만을 의미한다고 볼 수는 없으므로
이 값은 검수 및 인계에 필요한 기간을 추정하기 위한 proxy로 사용한다.


##### 2) 일정 Buffer

기획 작업기간에도 일정 여유를 둔다.

기획 이슈의 예상 작업기간은 다음과 같이 계산한다.

`예상 작업기간 = orig_estimate / (8시간 × 담당자 availability)`

예를 들어 `orig_estimate = 40h`,
담당자의 `availability = 1.0`이라면
예상 작업기간은 5영업일이다.

이 예상기간과 Jira의 실제 `started → resolved` 사이의
경과 영업일을 비교하였다.

주말, 공휴일 및 해당 담당자의 PTO는 영업일 계산에서 제외하였다.

분석 결과는 다음과 같다.

- 분석 대상: 44건
- 예상기간보다 실제 경과 영업일이 길었던 이슈: 27건
- 예상기간 이하로 완료된 이슈: 17건
- `실제 경과 영업일 / 예상 작업기간` 중앙값: 약 1.04
- `실제 경과 영업일 / 예상 작업기간` 75% 지점: 약 1.24

즉 모든 이슈가 예상보다 오래 걸린 것은 아니지만,
과거 이슈의 약 75%를 포함하려면
예상 작업기간보다 약 24%의 일정 여유가 필요했다.

따라서 초기 일정 Buffer를 **25%**로 정의한다.

예를 들어 예상 작업기간이 8영업일이라면

`8 × 1.25 = 10영업일`

을 실제 일정에 확보한다.

여기서 25% Buffer는 실제 투입 공수를 25% 증가시키는 의미가 아니라,
협의, 대기, 수정, 병행 업무 등으로 인해 일정상 경과기간이 늘어날 가능성을 고려하여
캘린더에 확보하는 여유기간을 의미한다.


##### 3) 최종 정의

본 과제에서 "안정적인 기획 일정"은 다음 두 조건을 모두 만족하는 일정으로 정의한다.

1. `orig_estimate`와 담당자의 `availability`로 계산한 예상 기획기간에 25%의 일정 Buffer를 포함한다.
2. 기획 완료 후 개발 착수 전까지 Size에 따라 다음 기간을 확보한다.
   - S: 3영업일
   - M: 4영업일
   - L: 6영업일

실제 날짜 계산에는 단순 달력일이 아니라
주말, 공휴일, 담당자 PTO 및 availability를 반영한 영업일을 사용한다.

#### 8. 어느 수준을 넘으면 TF를 제안할 것인가

TF는 특정 공정에서 현재 인력만으로 마감일까지 필요한 작업량을 처리하기 어려운 경우 제안한다.

판단에 사용하는 부족 공수는 다음과 같이 정의한다.

`부족 공수 = 남은 필요 MD - 마감일까지 현재 인력이 처리할 수 있는 가용 MD`

여기서 각 공정의 마감일과 남은 가용 MD는 이후 일정 역산 단계에서
주말, 공휴일, PTO, availability를 반영하여 계산한다.

TF 제안 기준은 **해당 공정 평균 인력 1명의 1주 가용 공수**로 정의한다.

즉,

`TF 기준 = 공정별 평균 availability × 5영업일`

로 계산한다.

현재 `people.csv`의 availability를 적용하면 다음과 같다.

| 공정 | 평균 availability | 1인 1주 가용 공수 | TF 제안 기준 |
|---|---:|---:|---:|
| PLAN | 0.80 | 4.00 MD | 부족 공수 4.0 MD 이상 |
| DEV | 약 0.88 | 약 4.42 MD | 부족 공수 약 4.4 MD 이상 |
| ART | 0.95 | 4.75 MD | 부족 공수 약 4.8 MD 이상 |

이 기준을 사용하는 이유는 부족 공수가 이 수준을 넘는다는 것은
해당 공정의 평균적인 인력 한 명을 약 1주 동안 추가 투입해야 할 정도의
작업량이 부족하다는 의미이기 때문이다.

그보다 작은 부족량은 우선 일정 buffer, 업무 재배치, 우선순위 조정 등으로
해결할 수 있는 범위로 보고 TF를 바로 제안하지 않는다.

예를 들어 개발 공정에서 마감일까지 필요한 잔여 작업이 15 MD이고
현재 개발 인력이 처리할 수 있는 가용량이 9 MD라면,

`부족 공수 = 15 - 9 = 6 MD`

이다.

개발 TF 기준인 약 4.4 MD를 초과하므로
추가 개발 인력 투입을 TF 대안으로 제안한다.

QA는 현재 `people.csv`에 QA 인력과 availability 정보가 없으므로
동일한 방식의 숫자 기준을 계산할 수 없다.
향후 QA 인력 정보가 추가되면 동일하게
`평균 availability × 5영업일` 규칙을 적용한다.

실제 남은 기간과 가용 MD의 계산은
이후 일정 역산 단계에서 본 기준에 맞도록 구현한다.

### A-3. 기록이 빠진 데이터 다루기

앞서 버전 종료 시점을 Jira Version Close로 정의했으므로,
기준일 현재 종료된 v1.3 ~ v1.9의 이슈를 대상으로 worklog 결측률을 계산하였다.

Done 및 Won't Do 상태의 이슈는 모두 실제 작업 공수가 발생할 수 있으므로
분석 대상에 포함하였다.

분석 결과 총 251개 이슈 중

- worklog가 존재하는 이슈: 160건
- worklog가 존재하지 않는 이슈: 91건
- worklog 결측률: 36.3%

이었다.

공정별 결측률은 다음과 같다.

| 공정 | 전체 이슈 | Worklog 없음 | 결측률 |
|---|---:|---:|---:|
| PLAN | 45 | 26 | 57.8% |
| DEV | 141 | 53 | 37.6% |
| ART | 65 | 12 | 18.5% |

이슈 유형별로도 차이가 있었다.

| Type | 전체 이슈 | Worklog 없음 | 결측률 |
|---|---:|---:|---:|
| Bug | 30 | 15 | 50.0% |
| Story | 169 | 72 | 42.6% |
| Task | 52 | 4 | 7.7% |

따라서 worklog 결측은 모든 이슈에서 동일한 확률로 발생한다고 보기 어렵다.

PLAN은 절반 이상이 누락된 반면 ART의 누락률은 20% 미만이고,
Bug와 Task 사이에서도 결측률 차이가 크다.


#### 전체 Actual MD를 추정할 것인가

남아 있는 worklog에 단순한 보정 배율을 적용하여
전체 실제 MD를 추정하지 않는다.

예를 들어 전체 기록률이 약 63.7%라는 이유로

`기록된 MD / 0.637`

과 같이 전체 MD를 계산하려면,
worklog가 존재하는 이슈가 결측 이슈를 대표한다는 전제가 필요하다.

그러나 실제 데이터에서는 공정 및 이슈 유형별 결측률이 크게 다르기 때문에
이 전제가 성립한다고 보기 어렵다.

단순 확대 추정을 할 경우 worklog를 상대적으로 잘 기록한 공정이나
이슈 유형의 특성이 전체 MD에 과도하게 반영될 수 있다.


#### 결측 Worklog의 대체 지표

worklog가 없는 이슈에는 `orig_estimate`를 참고용 대체 지표로 사용한다.

91개의 worklog 결측 이슈 중 71건(약 78.0%)에는
`orig_estimate`가 존재한다.

다만 `orig_estimate`는 실제 투입 공수가 아니라 작업 시작 전에 입력한
최초 예상 공수이므로 이를 실제 MD로 변환하여 합산하지 않는다.

따라서 다음과 같이 구분한다.

- worklog 존재 → 실제 관측 MD(`observed_actual_md`) 계산
- worklog 없음 + orig_estimate 존재 → 실제 MD는 UNKNOWN,
  `orig_estimate / 8`을 참고 계획 MD로 별도 표시
- worklog와 orig_estimate 모두 없음 → 실제 MD와 예상 MD 모두 UNKNOWN

버전별 실적을 표시할 때에도
관측된 실제 MD와 worklog 기록률을 함께 제공한다.

즉 기록된 값과 추정값을 합쳐 하나의 "실제 MD"로 만들지 않는다.


#### 이 판단이 틀렸을 경우의 영향

만약 실제로 worklog 결측이 무작위로 발생하고
남아 있는 worklog만으로도 전체 공수를 충분히 추정할 수 있었다면,
본 방식은 활용 가능한 데이터를 보수적으로 사용하게 된다.

이 경우 실제 총 MD를 완전히 복원하지 못하므로
baseline 갱신에 사용할 수 있는 실적 표본이 줄고,
기존 baseline의 개선 속도가 느려질 수 있다.

반대로 불완전한 worklog를 이용해 전체 MD를 강제로 추정했는데
결측이 현재 분석처럼 특정 공정이나 이슈에 편중되어 있다면,
잘못된 actual MD가 baseline에 반영된다.

그 결과 다음 버전에서 필요한 기획·개발·아트 공수가
과대 또는 과소 계산될 수 있고,
기획 착수일과 TF 판단까지 잘못될 수 있다.

따라서 본 과제에서는 하나의 완전한 실제 MD를 억지로 만드는 것보다
관측값과 추정값을 분리하여 데이터의 불확실성을 명확하게 유지하는 것을 우선한다.

### A-4. 시간에 따른 변화 읽기

v1.3부터 v2.0까지 버전별 이슈 수, worklog 기록률,
기록된 실제 MD, 계획 배포일 대비 실제 배포 지연을 비교하였다.

복수 Fix Version이 지정된 이슈는 어느 버전에 공수를 귀속할지
명확하지 않으므로 버전별 추세 분석에서는 제외하였다.


#### 1. 최근 버전에서 배포 지연이 반복되고 있음

계획 배포일과 실제 배포일의 차이는 다음과 같았다.

| 버전 | 계획 대비 실제 배포 지연 |
|---|---:|
| v1.3 | +6일 |
| v1.4 | 0일 |
| v1.5 | +15일 |
| v1.6 | +5일 |
| v1.7 | +8일 |
| v1.8 | +11일 |
| v1.9 | +11일 |
| v2.0 | +11일 |

초기 버전에서는 지연 폭이 일정하지 않았지만,
최근 v1.8 ~ v2.0은 세 버전 연속으로 계획보다 11일 늦게 배포되었다.

따라서 최근의 일정 지연은 일회성 예외라기보다
반복적으로 발생하고 있는 문제로 볼 수 있다.

이는 기존 baseline을 고정값으로 유지하는 방식보다
버전 종료 후 실제 실적을 지속적으로 다시 반영하는 구조가 필요하다는 근거가 된다.


#### 2. 최근 버전의 Worklog 기록률이 낮은 상태로 유지되고 있음

버전별 worklog 기록률은 다음과 같았다.

| 버전 | Worklog 기록률 |
|---|---:|
| v1.3 | 67.7% |
| v1.4 | 75.7% |
| v1.5 | 70.0% |
| v1.6 | 52.8% |
| v1.7 | 73.3% |
| v1.8 | 55.3% |
| v1.9 | 57.1% |
| v2.0 | 53.4% |

특히 최근 v1.8 ~ v2.0은 계속 50%대 수준이다.

따라서 최근 버전이라는 이유만으로 해당 버전의 recorded MD를
baseline에 그대로 반영하는 것은 위험하다.

예를 들어 v1.8의 recorded MD는 72.9 MD로 주변 버전보다 크게 낮지만,
동시에 worklog 기록률도 55.3%에 불과하다.

따라서 이 값을 곧바로
"v1.8에서는 실제 작업량이 크게 줄었다"고 해석할 수 없다.


#### 3. 최근 버전의 작업 규모는 커졌지만 데이터 신뢰도는 같이 좋아지지 않음

단일 Version에 속한 이슈 수는

- v1.8: 38건
- v1.9: 49건
- v2.0: 58건

으로 최근 버전에서 증가하였다.

반면 같은 기간 worklog 기록률은 약 53~57% 수준에 머물렀다.

즉 추적해야 할 작업은 늘어나고 있지만
실제 공수를 측정하기 위한 기록 품질은 함께 개선되지 않은 상태이다.


#### Baseline 운영에 미치는 영향

위 결과를 바탕으로 baseline은
마지막 한 개 버전의 recorded MD만 이용하여 자동 갱신하지 않는다.

버전별 actual MD와 함께 worklog 기록률을 같이 관리하고,
기록률이 낮은 버전의 실적은 신뢰도가 낮다는 표시를 남긴다.

또한 여러 종료 버전의 실적을 함께 이용하여
특정 버전의 이상치가 baseline을 크게 변경하지 않도록 한다.

v2.0은 실제 배포는 완료되었지만
과제 기준일 현재 Jira Version이 아직 Close되지 않았으므로
A-2에서 정한 버전 종료 기준에 따라 최종 baseline 갱신에는 사용하지 않는다.

즉 v2.0은 추세 확인을 위한 잠정 데이터로만 보고,
Jira Close 이후 최종 실적을 확정한다.
