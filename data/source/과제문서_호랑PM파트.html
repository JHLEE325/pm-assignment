1. 배경

호랑 PM파트는 업데이트 버전마다 기획 착수가 늦어져 개발 일정이 압축되는 문제를 겪고 있습니다.

원인을 추적해 보니, 프로젝트 초기에 수기로 만든 MD 기준표(md_baseline_v0.csv)가 한 번도 갱신되지 않은 채 2년째 쓰이고 있었습니다. 실제로 얼마나 일했는지는 Jira에 계속 쌓이고 있지만, 그 실적이 기준표로 되돌아오는 경로가 없습니다.

그래서 다음과 같은 순환 구조를 만들려 합니다.

버전 종료 → 실제 투입 MD 자동 측정 → 기준표 갱신
→ 갱신된 기준표로 다음 버전의 기획 착수일 역산
→ 담당 기획자·파트 리더에게 통지 → (다음 버전 종료 시 반복)

첨부된 데이터와 HTML 목업은 이 구조를 만들려다 중단된 상태입니다. 이어서 설계해주시면 됩니다.

콘텐츠는 시스템 / 콘텐츠 2개 카테고리와 S / M / L 3개 규모로 구분한다고 가정합니다.

3. 산출물 A — 데이터 진단과 기준 정하기

분량: 5페이지 이내

A-1. 데이터를 그냥 더하면 틀리는 지점 찾기

첨부된 데이터로 "이 버전에 MD가 총 몇 들었나"를 계산할 때, 단순히 숫자를 합치면 잘못된 값이 나오는 지점들이 있습니다. 찾아내서 어떤 이슈 번호가 그 예시인지와 함께 제시해주세요.

항목마다 다음 네 가지를 써주세요.

  1. 무엇을 발견했는지
  2. 왜 그게 문제인지
  3. 어떻게 처리할 생각인지
  4. 그렇게 처리하면 대신 생기는 부작용은 무엇인지

A-2. 정의가 없는 항목을 직접 정하기

아래 항목들은 데이터에 정의가 없습니다. 직접 정하고 그 근거를 써주세요. 정답은 없습니다. 정의끼리 서로 모순되지 않게 정해주세요.

  • 1 MD란 무엇인가. 사람 한 명이 하루 일한 것인지, 여러 사람이 동시에 한 이슈를 맡았을 때는 어떻게 나눌 것인지.
  • 이슈를 어느 공정(기획 / 개발 / 아트 / QA)에 귀속시킬 것인가. 데이터에는 공정을 나타내는 칸이 없습니다. 귀속 규칙을 정하고, 규칙에 들어맞지 않는 이슈는 어떻게 처리할지 써주세요.
  • QA MD는 측정할 수 있는가. 기준표에는 QA MD 칸이 있습니다. 제공 데이터로 이 값을 측정할 수 있는지 확인하고, 불가능하다면 무엇으로 대체할지 정해주세요.
  • 리소스 MD는 어디까지 포함하는가. 외주 아트 작업이 계정 하나로만 기록되어 있는데, 이걸 어떻게 쪼갤 것인지.
  • "버전이 종료됐다"는 시점은 언제인가. 계획 배포일, 실제 배포일, Jira에서 버전을 닫은 날 중 무엇을 쓸 것이며 왜 그런지.
  • S / M / L을 사람 감각이 아니라 눈으로 확인할 수 있는 기준으로 다시 정의하기. 지금은 기획자가 주관적으로 붙이고 있습니다.
  • "안정적인 기획 일정"이란 무엇인가. 개발 착수 며칠 전에 기획이 끝나야 하는지, 검수에 며칠이 필요한지, 여유(버퍼)를 몇 % 둘 것인지를 숫자로 정해주세요.
  • 어느 수준을 넘으면 TF를 제안할 것인가. 그 숫자가 왜 그 숫자인지도 함께.

A-3. 기록이 빠진 데이터 다루기

작업 시간 기록(worklog)이 꽤 많이 비어 있습니다. 실제 결측 비율을 직접 계산하고, 남은 기록으로 전체를 추정할지 아니면 다른 대체 지표를 쓸지 선택해주세요. 그리고 그 선택이 틀렸을 경우 무엇이 망가지는지 써주세요.

A-4. 시간에 따른 변화 읽기

v1.3부터 v2.0까지를 시간 순으로 놓고 봤을 때 눈에 띄는 추세나 변화가 있다면 기술하고, 그것이 기준표 운영 방식에 어떤 영향을 주는지 써주세요.

4. 산출물 B — Jira 데이터를 DB로 가져오는 방법 설계

분량: 8페이지 이내 (DDL, 쿼리, README는 분량에서 제외)

B-1. 원본을 열어보고 문제 찾기

jira_api_raw_sample.json을 열어보세요. 이 데이터를 아무 가공 없이 그대로 DB에 넣으면, A-2에서 정한 MD를 계산할 수 없습니다. 어디가 걸림돌인지 찾아서 "무엇이 문제인지"와 "그래서 어떻게 손봐야 하는지"를 써주세요. Jira에 추가로 요청해야 할 정보가 있다면 그것도 적어주세요.

B-2. 어느 값을 어느 칸에 넣을지 정리표 만들기

원본 데이터의 어느 항목이 DB의 어느 칸으로 들어가는지 표로 정리해주세요. 최소 10개 항목을 다뤄주시고, 항목마다 원본에서의 위치, DB 칸 이름, 데이터 종류, 넣기 전에 바꿔야 할 것, 값이 비었을 때의 처리, 나중에 Jira 쪽이 바뀌면 받는 영향을 채워주세요.

원본에는 customfield_10016처럼 이름만 봐서는 무슨 값인지 알 수 없는 항목이 있습니다. 이걸 코드에 그대로 적어두면 Jira에서 항목 번호가 바뀌는 순간 시스템이 멈춥니다. 이를 피하는 방법도 제안해주세요.

B-3. "언제부터 언제까지 일했는지" 알아내기

MD를 계산하려면 각 작업이 실제로 언제 시작되고 끝났는지를 알아야 합니다. 그런데 Jira에는 "작업 시작일"이라는 항목이 따로 없고, 대신 상태가 바뀐 기록(할일 → 진행중 → 완료)만 남아 있습니다.

이 상태 변경 기록을 DB에 어떤 모양으로 저장할지 설계하고, 거기서 실제 작업 기간을 뽑아내는 규칙을 써주세요. 특히 "검토 대기"나 "보류" 상태로 멈춰 있던 기간을 작업 시간에 포함할지 뺄지 정하고 이유를 밝혀주세요.

B-4. 데이터를 얼마나 자주, 어떻게 가져올지

다음을 정하고 근거를 써주세요.

  • 매번 전체를 다시 가져올지, 바뀐 것만 골라 가져올지(증분 동기화)
  • 바뀐 것만 가져온다면 "어디까지 가져왔는지"를 무엇으로 기억할지, 그 방법의 한계는 무엇인지
  • 몇 시간(또는 며칠) 간격으로 돌릴지
  • 같은 데이터가 실수로 두 번 들어와도 결과가 망가지지 않게 만드는 방법
  • Jira가 "요청이 너무 많다"며 거부할 때 어떻게 다시 시도할지
  • 이미 배포가 끝난 버전의 이슈를 누군가 나중에 수정했을 때, 확정해 둔 MD를 그대로 둘지 다시 계산할지

B-5. 데이터를 몇 단계로 나눠 보관할지

Jira에서 받은 원본을 파일 형태로 그대로 남길지 정하고, 남긴다면 왜 남기는지, 어떤 형식과 폴더 구조로 쌓을지, 그리고 나중에 계산 규칙이 바뀌어서 과거 데이터를 전부 다시 계산해야 할 때 어떤 순서로 복구할지 써주세요. 원본을 안 남기는 선택도 괜찮지만 그때 생기는 위험을 밝혀주세요.

B-6. DB 테이블 설계

받은 그대로 쌓는 단계, 다듬는 단계, 합쳐서 요약하는 단계로 나누어 테이블을 설계하고 생성 구문(DDL)을 작성해주세요. 저장 방식·정렬 기준·데이터를 나눠 담는 기준을 각각 왜 그렇게 정했는지 한 줄씩 붙여주세요.

이 정도 데이터 양(연간 2천 건 수준)에 ClickHouse는 과한 선택이다라고 판단하셔도 됩니다. 그렇다면 대안을 제시하고 비교해주세요.

B-7. 핵심 조회 쿼리 2개

① 버전별로 카테고리 × 규모별 실제 MD를 뽑는 쿼리, ② 특정 기간에 한 담당자가 동시에 몇 건을 맡고 있었는지 뽑는 쿼리. 제공된 CSV를 B-6에서 설계한 테이블에 실제로 적재한 뒤 쿼리를 실행하고, 결과 예시를 함께 제출해주세요.

DB 종류는 자유이며 SQLite처럼 가벼운 것도 괜찮습니다. 설치·적재·실행 과정과 함께, 적재하면서 손봐야 했던 데이터와 그 처리 방법을 README에 남겨주세요.

B-8. 측정한 MD를 기준표로 되돌리는 규칙

측정된 실적이 기준표로 돌아가는 규칙을 설계하고, 최소한 다음에 답해주세요.

  • 기존 값을 덮어쓸 것인가, 버전별로 쌓아둘 것인가
  • 유난히 이상했던 버전 한 건이 기준을 망가뜨리는 것을 어떻게 막을 것인가. (최근 몇 개의 평균을 쓸 것인지, 이상한 값을 걸러낼 것인지, 무엇을 "이상하다"고 볼 것인지)
  • 자동으로 반영할 것인가, 사람이 승인해야 반영할 것인가. 승인자는 누구이고, 무엇을 보고 판단하는가
  • 기준표가 바뀌면 이미 통지해 둔 일정은 어떻게 처리할 것인가

B-9. Jira 쪽이 바뀌었을 때 대응

운영하다 보면 Jira에 입력 항목이 생기거나 없어지거나 이름이 바뀌고, 업무 흐름의 상태 이름도 바뀝니다. 이때 시스템이 조용히 잘못된 값을 만들어내지 않도록 무엇을 어떻게 감지하고, 감지한 다음 어떤 순서로 처리할지 써주세요.

"조용히 잘못된다"가 핵심입니다. 눈에 보이는 오류는 금방 고치지만, 그럴듯하게 틀린 숫자는 몇 달 뒤에 발견됩니다.

B-10. 값이 맞는지 계속 확인하는 장치

DB에 들어간 값이 Jira 화면의 값과 실제로 일치하는지 상시 확인하는 방법을 3개 이상 제시해주세요. 무엇을 비교할지, 얼마나 자주 할지, 몇 %까지 차이를 허용할지, 차이가 났을 때 무엇을 할지를 포함해주세요.

5. 산출물 C — 기획 착수일 역산 상황판 (HTML 1개)

분량: HTML 1개 + 설명 문서 2페이지 이내

dashboard_mockup.html을 수정하거나 새로 작성해주세요. 데이터는 임의의 값으로 대체 가능하며, 실제 DB 연결은 요구하지 않습니다. 목업에는 의도적으로 잘못된 부분이 8곳 있고 주석으로 표시되어 있습니다.

C-1. 기획 착수일 역산

업데이트일, 콘텐츠, 담당 기획자를 지정하면 언제 기획을 시작해야 하는지를 거꾸로 계산해 보여주세요. 기획 → 검수 → 리소스 선행 → 개발 → QA/코드프리즈 흐름이 모두 보여야 하고, 주말·공휴일·연차·담당자 가용률·동시에 맡고 있는 건수가 반영되어야 합니다.

C-2. 일정이 넘칠 때 대안 제시

"지연"이라고만 표시하고 끝내지 말고, 실제로 선택할 수 있는 대안을 2개 이상 숫자 근거와 함께 제시해주세요. 예를 들어 TF를 꾸릴 때 몇 명이 며칠 필요한지, 규모를 L에서 M으로 줄이면 며칠이 확보되는지, 업데이트를 미룬다면 최소 며칠이 필요한지 같은 것들입니다.

C-3. 화면이 필요한 데이터 형태 정의하기

함께 제공되는 /api/md_summary 규격은 화면이 필요한 값을 주지 못합니다. 화면이 요구하는 데이터의 모양을 직접 정의해 JSON 형태로 제출해주세요. 그리고 각 값이 B-6에서 설계한 테이블 중 어디서 오는지, 어느 단계에서 계산되는지(DB 쿼리 / 서버 배치 작업 / 화면 스크립트 / 조건에 따른 기계적 판단 / AI 호출)를 표로 연결하고, 왜 그렇게 나눴는지 써주세요.

분량: 3페이지 이내

D-2. AI를 어디에 쓰고 어디에 쓰지 않을지

알림을 만드는 과정에서 조건에 따라 기계적으로 처리할 부분과 AI에게 맡길 부분을 나누고 이유를 써주세요. 월 사용량과 비용을 추정하되 어떤 가정으로 계산했는지 밝히고, 비용을 절반으로 줄여야 한다면 무엇을 먼저 기계적 처리로 내릴지 써주세요.
